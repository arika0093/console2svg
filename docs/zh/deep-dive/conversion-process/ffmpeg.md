---
title: 转换为视频 (ffmpeg)
description: 将 SVG 状态序列栅格化为 PNG 流，并用 ffmpeg 编码为视频和图片格式的路径。
---

视频并不是简单连接 SVG。浏览器可以解释 SMIL，但常见视频容器无法直接放入带时间的 SVG DOM，因此需要把各个时刻转换为栅格帧，再作为时间序列传给 ffmpeg。由于转换入口统一为 SVG，视频也会使用与静态 SVG 相同的主题、chrome、遮罩和框线绘制。

## 为什么不创建临时文件序列

以前“把 SVG/PNG 做成序列文件再传给 ffmpeg”的方式，会让磁盘 I/O、清理工作、Windows 上的文件锁随视频时长增加。现在的视频路径会在内存中生成 PNG，并按顺序写入 `image2pipe` 的标准输入。

由于不把文件系统作为帧的中继点，可以减少生成完成前所需的临时区域和结束时的删除竞争。

PNG 化的 CPU 负载较高，因此会根据可用处理器数量最多并行启动 8 个任务。不过 ffmpeg 的输入必须保持原始顺序，所以会从等待队列以 FIFO 方式送入同一个标准输入。PNG 往往比 SVG 更大，因此复用同一 SVG 结果的缓存也限制为 16 个，避免长时间捕获无限制占用内存。

## 不以 ffmpeg 能读取 SVG 为前提

ffmpeg 的构建版本有时不包含用于 SVG 输入的 librsvg。仅凭可执行文件存在或 `-formats` 的显示并不能保证实际可以解码 SVG，因此启动前会尝试把最小 SVG 实际转换为 PNG，并缓存结果。

内存管道无法分隔并解释多个连接在一起的 SVG，因此视频路径始终会预先转换为 PNG。自动选择会优先使用捆绑的 resvg，其次是支持 SVG 的 ffmpeg、`rsvg-convert`，最后才是明确失败。ffmpeg 可以专注于最终编码，用户环境差异对 SVG 解释结果的影响范围也能缩小。

## 编解码器和偶数尺寸

MP4 会选择可用的 `libx264`；如果没有，则考虑 Windows Media Player 兼容性降级为 `mpeg4`。WebM 和 GIF 则交给 ffmpeg 针对容器的默认选择。

所有路径都会指定 `yuv420p` 和 `pad=ceil(iw/2)*2:ceil(ih/2)*2:0:0`。H.264 的 4:2:0 要求宽高为偶数，因此字体高度或 padding 组合造成的 1px 不足只会补到右端和下端。这是在不移动外观的前提下满足编码条件的修正。
