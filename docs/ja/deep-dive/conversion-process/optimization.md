---
title: 変換パイプラインの最適化
description: パース量、画面コピー、SVG の DOM 数、メモリ割り当て、ラスタライズ、ファイル I/O を減らす仕組み。
---

端末録画には、複数の段階で同じ情報が繰り返し現れます。
一回の画面更新が複数の PTY read に分かれ、隣接する画面では大半のセルが変化せず、アニメーションでは同じ行が何度も現れ、動画の固定 FPS サンプリングでは同一画面を複数回要求することがあります。
console2svg は後段の処理を高速化する前に、この重複を各段階で減らします。

## レンダリング前にイベント数を減らす

PTY から読んだ一回分を、そのまま一つの録画イベントにはしません。
短時間に連続した出力をまとめる処理を **出力コアレッシング** と呼び、`RecordingSession` に入るイベント数を抑えます。

既定のコアレッシング窓は、動画の一フレーム時間の4分の1です。
ただし2ミリ秒未満にはせず、20ミリ秒を超えないようにします。
一つのバッチが一フレーム時間を超えて成長し続けることも防ぎます。

この処理により、多数の小さな write で一画面を描く TUI でも、ANSI パーサーが処理するイベント境界を減らせます。

端末エミュレーション後には、別のフレーム削減を行います。
`TerminalEmulator.ReplayFrames` は画面内容のシグネチャを比較し、可視セルが変わらないイベントを新しいフレームとして保持しません。
正の FPS が指定されている場合は最小フレーム間隔も適用し、その区間に複数の変更があれば最後の変更状態を保留フレームとして採用します。
先頭状態と末尾状態は保持します。

静止画は通常一つの画面しか必要としないため、別の経路を使います。
デフォルトの静止画レンダリングでは、全イベントごとに `ScreenBuffer` のスナップショットを作らず、必要な時点まで一つのエミュレーターを進めます。
アニメーション用のスナップショット生成コストを静止画へ持ち込みません。

## 画面スナップショットを行単位で共有する

アニメーションで画面全体を毎回 deep copy すると、コピー量はフレーム数、行数、列数の積に比例します。
`ScreenBuffer` はこのコピーを避けるために **コピーオンライト** を使います。

可視画面のスナップショットを作るときは、行配列を指す外側の配列だけを複製します。
各行の `ScreenCell[]` は元の画面と共有します。
共有中の行を書き換える必要が生じた時点で、その行だけを複製します。

FPS 窓の中で使う保留フレームも同じ仕組みを利用します。
最新状態へ更新するときは全セルを再コピーせず、行参照とシグネチャ情報を差し替えます。

行共有は比較処理にも使います。
二つのスナップショットが同じ行配列を参照していれば、その行についてセル比較を行わず同一と判定できます。
参照が異なる行だけが実データ比較へ進みます。

## シグネチャを差分更新する

画面の比較には **ビジュアルシグネチャ** を使います。
各セルのシグネチャは文字列、表示スタイル、全角文字関連のフラグから作ります。
文字列とスタイルの hash には `XxHash3` を使い、ASCII 一文字の文字列シグネチャは事前計算します。

各行は、列位置を含めたセルシグネチャの組から64ビットの行シグネチャを持ちます。
シグネチャ追跡を開始した後は、一つのセルを書き換えるたびに行全体を再走査しません。
以前のセルの値を XOR で取り除き、新しいセルの値を XOR で加える形で行シグネチャを更新します。

画面全体のシグネチャは、各行のシグネチャから作ります。
`GetContentSignature` はカーソルを含めず、アニメーション本文を新しいフレームとして保持するかの判定に使います。
`GetVisualSignature` はカーソルの表示状態と位置も含み、最終的な描画状態を区別する用途で使います。

行シグネチャをまとめる一時バッファは、4096バイト以下なら `stackalloc` で確保します。
それを超える場合だけ `ArrayPool<byte>` から借ります。

## 文字列とスタイルを再利用する

端末出力では ASCII 一文字と同じ文字スタイルが繰り返し現れます。
console2svg は ASCII 128文字分の一文字 `string` を事前に作り、セル更新のたびに `char.ToString()` で新しい文字列を作らないようにします。

`CellStyle` も `ScreenBuffer` 内で共有します。
直前と同じスタイルが続く通常ケースでは、前回の `CellStyle` をそのまま使います。
離れた位置で同じスタイルが再登場した場合は、上限付きの辞書から再利用します。

RGB 色を連続して切り替える入力で辞書が増え続けないよう、スタイルキャッシュは256件を超えると再構築します。

頻繁に使う辞書操作では、必要な箇所で `CollectionsMarshal.GetValueRefOrAddDefault` を使います。
「検索してから追加する」という二回の hash table 探索を、一回の slot 取得へまとめます。

## SVG の要素数と文字列量を減らす

SVG は一セル一要素では出力しません。

同じ非既定背景色が横に連続するセルは、一つの矩形へまとめます。
同じ前景スタイルが続くセルは、一つの `<text>` へ連結します。
途中の空白は、同じスタイルの後続文字へつながる場合だけ保持し、行末の空セルは出力しません。
全角文字と図形として描く文字は、列位置を壊さないよう文字列 run の境界にします。

同じ文字スタイルは `SvgStyleRegistry` が短い CSS class へ割り当てます。
再利用可能な定義内で同じ矩形や path が現れた場合は、`SvgElementRegistry` が最初の要素へ ID を付け、以後を `<use>` に置き換えます。

罫線文字は SVG を書く前に水平線分と垂直線分へ変換します。
同じ位置、色、線幅で接続できる線分を結合し、同色の矩形を一つの path data に集約します。

この罫線結合を導入したコミットの btop ベンチマークでは、対象 SVG が68.5 KBから31.3 KBへ減り、罫線 path 数は417個から5個へ減りました。
この値はその時点の btop 入力に対する測定結果であり、任意の端末出力に同じ削減率を保証するものではありません。

`SvgWriter` は数値出力でも一時文字列を減らします。
整数と浮動小数点数は `TryFormat` で stack 上の文字バッファへ書き、その span を直接 writer へ渡します。
`StringBuilder` も全体を `ToString()` せず、`GetChunks()` で既存チャンクを順に書き出します。

## アニメーションを行単位で重複排除する

アニメーション SVG は、保持した全フレームの画面全体を複製しません。
`PrepareAnimatedRows` は **行カタログ** を作り、同じ行内容を一度だけ定義します。

最初の候補検索には行のビジュアルシグネチャを使います。
同じシグネチャを持つ候補が見つかっても、実際のセル内容を比較してから再利用します。
hash 衝突だけで誤った行へ置き換わることはありません。

新しい一意行が見つかった時点で、その行の文字スタイルも収集します。
全フレームを一度スタイル走査してから別の pass で行を重複排除する方式ではなく、行カタログ作成とスタイル収集を同じ走査にまとめています。

## 小さな行変更を差分として保持する

一行の一部だけが変わった場合は **行差分** を使えることがあります。
直前の行定義を `<use>` で参照し、変更した列範囲だけを上から描きます。

差分範囲は16列以下で、かつ可視幅の4分の1以下でなければなりません。
差分の参照深度は4段未満に制限します。
ファイルサイズを減らす代わりに、深い `<use>` 連鎖を SVG レンダラーへ押し付けないためです。

変更境界が全角文字の継続セルに触れる場合は、文字を分断しないよう範囲を広げます。

手動マスクパターンがある場合は行差分を使いません。
パターンが「変更していない基底部分」と「差分部分」をまたぐと、分割後の文字列だけでは一致を検出できないためです。

## 描画用の一時領域を再利用する

行定義を SVG へ落とす処理では、罫線の水平線分、垂直線分、角丸、ブロック矩形、結合済み矩形などの一時 List が必要です。
`FrameRenderWorkspace` はこれらを一度保持し、行定義ごとに `Clear()` して再利用します。

前景文字、マスク検出用の正規化文字列、path data の `StringBuilder` も同じ workspace に置きます。
一意行の数だけ同種の一時オブジェクトを作ることを避けます。

可視行は inner loop の外で `GetVisibleRow` から span として取得します。
scrollback を使わない通常経路では、セルごとに汎用アクセサーを呼びません。

## SMIL を行の継続区間ごとに出力する

行定義を重複排除した後も、全フレームへ一つずつ `<use>` を出しません。
同じ物理行が同じ行定義を参照し続ける連続区間を一つの run にまとめます。

一つの `<use>` がその run を表し、`display` の discrete な SMIL animation が表示時間を決めます。
カーソルも本文とは別の run としてまとめるため、カーソル移動だけで行本文を複製しません。

この構造では、DOM 数が単純な「フレーム数 × 行数」ではなく、各行の内容が実際に切り替わった回数へ近づきます。

## 動画で SVG と PNG を二段階に再利用する

固定 FPS の動画フレーム生成では、一つの `TerminalEmulator` を録画の先頭から順に進めます。
サンプルごとにイベント0から再生し直しません。
時刻が進むにつれてイベント index も前方向にだけ進みます。

静止 SVG は画面のビジュアルシグネチャを key にして最大128件キャッシュします。
同じ画面が再登場した場合は、同じ内容の新しい文字列を作らず、キャッシュ内の同じ SVG `string` オブジェクトを返します。

動画 converter は、この object identity を PNG キャッシュの key にします。
同じ画面は **二段キャッシュ** により、SVG の再生成だけでなく PNG の再ラスタライズも避けられます。
巨大な SVG 文字列の内容を比較する必要もありません。

PNG は SVG より大きくなることがあるため、PNG キャッシュは16件に制限します。

SVG から PNG への変換は CPU 数に応じて並列化し、最大8件までに制限します。
完成した PNG は bounded FIFO から ffmpeg へ元の順序で書きます。
全動画分の PNG を先にメモリへ作り切ることはありません。

## フレーム転送をメモリ内で完結させる

動画一本につき ffmpeg process は一つだけ起動します。
PNG フレームは `image2pipe` の標準入力へ直接書き、通常経路では連番 PNG ファイルを中継しません。

同梱 resvg も process 内で呼び出します。
system font database は一度だけ初期化して後続フレームで共有します。
SVG をネイティブ側へ渡す UTF-8 buffer は `ArrayPool<byte>` から借ります。

これにより、フレームごとの process 起動とファイル作成、再読込、削除を通常の動画経路から外しています。

## 最適化を工程ごとに測定する

benchmark project は、端末 replay、production frame 作成、一意行カタログ生成、行定義の出力、SMIL の出力、静止 SVG、アニメーション SVG、実際の asciicast 入力を分けて計測します。
FPS と自動マスクの有無も別条件として測定できます。

`MemoryDiagnoser` では managed allocation と GC を記録します。
Linux で `perf` を利用できる場合は、retired instructions、cycles、branches、cache misses、CPU sampling、render から buffer 更新までの深い disassembly も取得できます。

SVG の byte 数を減らす変更と、生成 CPU を減らす変更と、allocation だけを減らす変更は効果が異なります。
工程を分けて測ることで、それぞれを同じ指標として扱わずに評価できます。
